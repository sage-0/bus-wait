# スクールバス待ち行列可視化システム 設計書 (ドラフト)

**版数**: 0.2 (ドラフト)
**日付**: 2026-08-10
**対象**: 東京工科大学 八王子キャンパス スクールバス (八王子駅 / 八王子みなみ野駅 系統)

---

## 1. 目的と非目標

### 1.1 目的

キャンパスおよび最寄り2駅のバス停における待ち行列の混雑状況を、追加の固定設備なしに可視化する。利用者が「今バス停に向かうと、どのくらい待つか」を事前に把握できることを目標とする。

### 1.2 非目標 (明示的にやらないこと)

| 項目 | 理由 |
|---|---|
| **正確な待ち人数の計測** | 必要なのは混雑の有無であり、人数の絶対値ではない。またアプリ普及率が不明なため、観測人数から実人数を推定する経路は原理的に破綻する |
| 固定ハードウェアの新規設置 | 制約条件。BLEビーコンは将来の任意拡張として保留 (10章) |
| 未登録者の計測 | アプリ登録者のみを対象とする |
| ストア審査対応 | 当面 TestFlight / 内部配布のため範囲外 |
| リアルタイム性 (秒単位) | 数分の遅延を許容する。OSのバックグラウンド制約と両立しないため |

### 1.3 中核となる設計判断

**人数を数えるのではなく、待ち時間そのものを測る。**

利用者一人あたりの「バス停到着 → 乗車」の所要時間を実測し、その分布から混雑度を導出する。この方式は観測者が1人でも成立し、アプリ普及率に依存しない。

## 2. 全体アーキテクチャ

```
[端末]                          [サーバー]
 ジオフェンス監視
   ↓ 進入/退出を検知
 生イベント + タイムスタンプ  ──→  イベント受信API
   (判定は一切しない)                ↓
                                  セッション構成
                                    ↓
                                  発車イベント検出 (複数人の同時離脱)
                                    ↓
                                  往復照合による乗車確定
                                    ↓
                                  待ち時間の統計化
                                    ↓
 混雑度表示           ←──────────  混雑度API
```

### 2.1 端末を「薄く」する原則

端末側は**判定を行わず、生イベントの記録と送信のみ**を担当する。理由は以下の通り。

- iOS のリージョン退出判定には独自のヒステリシスがあり、実際の退出から数分遅れて発火する。端末が算出した滞在時間は信用できない
- Android は `GEOFENCE_TRANSITION_DWELL` を持つが iOS には存在しない。判定を端末に置くとOS差が仕様差になる
- 発車イベントの検出は複数ユーザーの横断的な相関を要するため、端末単体では原理的に不可能

サーバー側で判定を一元化することで、端末の退出時刻が数分ブレても、後述するクラスタリングの中央値で吸収できる。

## 3. ジオフェンス定義

### 3.1 監視リージョン一覧

登録するリージョンは **3件のみ**。iOS のリージョン監視上限 (20件) に対して十分な余裕がある。

| ID | 名称 | 中心 (緯度, 経度) | 半径 | 備考 |
|---|---|---|---|---|
| `campus_area` | キャンパス側バス停エリア | 35.625514, 139.341597 | 150 m | 2バス停の中間点。起床トリガー専用 |
| `st_hachioji` | 八王子駅ロータリー | 35.654167, 139.339194 | 150 m | 実際の待機列位置にピン設置済み |
| `st_minamino` | 八王子みなみ野駅ロータリー | 35.631472, 139.329278 | 150 m | 同上 |

**リージョン間距離** (相互干渉がないことの確認):

- `campus_area` ↔ `st_hachioji`: 約 3.2 km
- `campus_area` ↔ `st_minamino`: 約 1.3 km
- `st_hachioji` ↔ `st_minamino`: 約 2.7 km

いずれも半径150mの円が重なる余地はない。

### 3.2 キャンパス側の2段構え方式

キャンパス側の2バス停は **約113m しか離れていない**。

| ID | 名称 | 中心 (緯度, 経度) | 目印 |
|---|---|---|---|
| `campus_hachioji_bound` | 八王子駅行き のりば | 35.625806, 139.342111 | セブン-イレブン片柳学園店 側 |
| `campus_minamino_bound` | みなみの駅行き のりば | 35.625222, 139.341083 | 講義棟B 側 |

この距離に対して個別のジオフェンスを張る方式は採用しない。iOS のリージョン監視は基地局・Wi-Fi測位ベースであり、**半径100m未満では発火が不安定になり取りこぼしが生じる**。一方、113m離れた2点に半径100mの円を置けば必ず重なる。

そこで以下の2段構成とする。

**第1段: 起床トリガー**
中間点に半径150mのリージョン (`campus_area`) を1つだけ登録する。発火の信頼性を優先し、この時点ではどちらののりばかを判定しない。

**第2段: のりば判別**
起床後、`desiredAccuracy = Best` で高精度測位を最大60秒間だけ実行し、2点との距離を比較して判別する。

```
d_A = 現在地から campus_hachioji_bound までの距離
d_B = 現在地から campus_minamino_bound までの距離

if |d_A - d_B| >= 35m:
    → 近い方ののりばに確定
else:
    → 保留 (pending)。10秒間隔で再測位し、最大60秒まで再試行
```

しきい値35mは、市街地GPSの誤差 (5〜20m) に対する安全マージンとして設定する。保留のまま確定できなかったセッションは統計から除外するが、生データは保持して後日のしきい値調整に用いる。

前景での高精度測位は最大60秒で打ち切るため、電池消費は許容範囲に収まる。

### 3.3 誤爆源と対策

| リージョン | 主な誤爆源 | 対策 |
|---|---|---|
| `campus_hachioji_bound` | コンビニの買い物客、広場の通過者 | 5.4 の乗車確定を通過しない限りカウントしない |
| `campus_minamino_bound` | 講義棟B内の在室者、移動中の学生 | 同上 |
| `st_hachioji` / `st_minamino` | 駅前の一般通行人 (桁違いに多い) | 同上。駅側では特に必須 |

**重要**: 「バス停エリアに入った人」を数えるのではなく、**「バスに乗って離脱したことが確認できた人」だけを遡って対象とする**。滞在時間の下限フィルタのみに頼るより確実に誤爆を排除できる。

### 3.4 駅側の系統判別が不要である理由

八王子駅とみなみの駅は約2.7km離れており、**どちらのリージョンに入ったかで乗車系統が一意に決まる**。当初検討していた「利用者に系統を事前選択させるUI」および「キャンパス側の判別結果を駅側のデフォルト値に流用する仕組み」は、いずれも不要のため破棄する。

## 4. 端末側イベント仕様

### 4.1 送信イベント

端末は以下のイベントを生成し、タイムスタンプ付きでサーバーに送る。判定・集計は行わない。

| イベント種別 | 発生契機 | 主要フィールド |
|---|---|---|
| `region_enter` | ジオフェンス進入 | `region_id`, `occurred_at` |
| `region_exit` | ジオフェンス退出 | `region_id`, `occurred_at` |
| `stop_resolved` | 第2段判別の完了 | `stop_id` または `pending`, `d_a`, `d_b`, `accuracy` |
| `motion_sample` | 測位ウィンドウ中の定期サンプル | `lat`, `lon`, `speed`, `heading`, `accuracy` |
| `boarding_hint` | 利用者の任意タップ (乗れた / 見送った) | `answer` |

すべてのイベントに端末生成の `event_id` (UUID v4) を付与し、サーバー側で冪等に扱う。オフライン時は端末にキューイングし、復帰時にまとめて送信する。**送信の遅延は許容されるが、`occurred_at` は必ず発生時刻を保持すること** (送信時刻ではない)。

### 4.2 `motion_sample` の取得範囲

常時測位は行わない。以下のウィンドウに限定する。

- のりば判別中 (最大60秒)
- `region_exit` 検知の前後 (退出方向・速度の判定用、最大120秒)

### 4.3 OS別の実装上の注意

**iOS**

- `CLLocationManager` のリージョン監視はアプリ終了後もバックグラウンド復帰する
- 監視上限20件 — 本システムは3件のため問題なし
- **dwell (滞在) イベントが存在しない** — 滞在判定はサーバー側で `t_now - t_in` により行う
- 退出判定に独自のヒステリシスがあり数分遅れる — 端末の退出時刻を信用しない設計により吸収

**Android**

- Geofencing API の上限は100件
- `GEOFENCE_TRANSITION_DWELL` が利用可能だが、**iOS と仕様を揃えるため使用しない**。滞在判定はサーバー側に統一する
- `ACCESS_BACKGROUND_LOCATION` が必要
- 最大のリスクは Doze と、Xiaomi / OPPO 等の OEM 独自プロセスキル。端末再起動後のジオフェンス監視の再登録処理は必須

**ライブラリ方針**

`background_geolocation` (transistorsoft製) は両OSの差異、OEMキル対策、再起動後の監視復帰までカバーするが、**初期段階では採用しない**。理由は以下の通り。

- 本システムが必要とするのは「3リージョンの監視」「60秒の測位ウィンドウ」「イベントのキューと送信」のみであり、同ライブラリの大半の機能 (activity recognition、自動同期、独自の滞在判定) は不要
- 特に**同ライブラリが内蔵する滞在判定・移動検知は 2.1 が禁じる「端末側の判定」そのもの**であり、無効化して使うことになる
- Android のリリースビルドには有料ライセンスが必要 (要確認)

ただし OEM キル (Xiaomi / OPPO 等) が実機で顕在化した場合の**差し替え先として保留**する。4.5 のアーキテクチャはネイティブ層をチャネルの裏に隠すため、差し替えは Dart 側に波及しない。

### 4.4 権限取得フロー

初回起動時にいきなり「常に許可」を要求しない。

1. まず「使用中のみ許可」で機能を体験させる
2. 利用実績が生じた後に「常に許可」への昇格を、必要性の説明とともに促す

TestFlight 配布でも「常に許可」のプロンプトは通常通り表示される。この流れは将来のストア申請時にもそのまま使える。

### 4.5 端末側の実装アーキテクチャ

**Flutter 1本 + 各OSネイティブの薄いバックグラウンド層**を採用する。

```
[Dart / Flutter]  UI・権限フロー・設定更新・混雑度表示・boarding_hint のタップ
       ↕ MethodChannel (設定の投入と状態の取得のみ。イベントは流さない)
[Swift]   CLLocationManager → ローカルキュー → HTTP送信
[Kotlin]  Geofencing API    → ローカルキュー → HTTP送信
```

**中核となる原則: ジオフェンス発火時に Dart を起こさない。**

イベントの記録・キューイング・送信はネイティブ層で完結させる。これにより以下が成立する。

- Flutter の background isolate (`@pragma('vm:entry-point')`) に起因する起動レース・プラグイン未登録といった障害を構造的に回避できる
- ネイティブ層は 2.1 の要求通り「イベントを JSON にして積むだけ」となり、判定ロジックを持たない
- ネイティブ層が Flutter に依存しないため、Dart 側を捨てても収集機能は残る

**責務分界**

| 層 | 責務 | 責務でないもの |
|---|---|---|
| Dart | UI、権限要求、設定の更新、状態表示 | イベントの生成 (`boarding_hint` を除く)、送信 |
| ネイティブ | 監視、測位、イベント生成、キュー、送信、設定の永続化 | 滞在時間の算出、混雑度の計算、のりばの最終確定以外の判定 |

**設定の永続化はネイティブ側が持つ。** アプリ終了後にジオフェンスが発火した時点で Dart は存在しないため、ネイティブ層は自身の永続設定のみで完結して動作できなければならない。Dart は設定を「更新する」のであって「供給する」のではない。

### 4.6 イベント送信ポリシー

**送信ジッター**

バス待ちは時限終了直後に集中するため、ジオフェンス発火も同時刻に集中する。利用者が千人規模に達した場合、一斉送信がサーバーに対する突発負荷となる。

対策として、送信時に **0〜120秒のランダム遅延**を挿入する。1.2 が「リアルタイム性 (秒単位) を非目標」とし、4.1 が `occurred_at` に発生時刻を保持することを要求しているため、**この遅延は統計精度を一切劣化させない**。

**キューと再送**

| 項目 | 値 | 備考 |
|---|---|---|
| 永続化 | iOS: SQLite / Android: Room | プロセスキル・再起動をまたぐ |
| バッチ上限 | 200 イベント / リクエスト | |
| 圧縮 | gzip | `motion_sample` が支配的なため効果が大きい |
| 再送間隔 | 30秒 → 1分 → 2分 → 5分 → 15分 → 60分 (上限) | 指数バックオフ |
| 削除条件 | サーバーが `event_id` を受理した後 | |

**キュー溢れ時の優先度**

キューが上限に達した場合、イベント種別の重要度に従って古いものから破棄する。

| クラス | 種別 | 破棄 |
|---|---|---|
| 必須 | `region_enter`, `region_exit`, `stop_resolved`, `boarding_hint` | **破棄しない** |
| 補助 | `motion_sample` | 古いものから破棄する |

`motion_sample` は 5.4 の速度フォールバックと較正 (10章) にのみ用いる補助データであり、欠落しても待ち時間の統計は成立する。逆に `region_enter` / `region_exit` の欠落はセッションそのものを失わせる。

**端末時計のずれ**

5.2 のクラスタリングは複数端末の `occurred_at` を横断比較するため、端末間の時計ずれがクラスタを破壊しうる。eps = 90秒に対し、手動で時刻設定した端末は分単位でずれうる。

対策として、リクエストのトップレベルに送信時点の端末時刻 `device_sent_at` を持たせる。サーバーは `received_at - device_sent_at` から時計ずれを推定し、閾値を超えるバッチにフラグを立てて**クラスタリングから除外する** (生データは 5.5 の原則通り保持)。

**端末側での補正は行わない。** 補正は判定であり、2.1 に反する。

### 4.7 MethodChannel の契約

```
channel: jp.ac.teu.buswait/geo
```

**Dart → Native**

| メソッド | 引数 | 戻り値 | 用途 |
|---|---|---|---|
| `configure` | config (6.2 の `GET /v1/config` の内容 + トークン) | void | 設定をネイティブ側に永続化する |
| `start` | — | void | 監視を開始する |
| `stop` | — | void | 監視を停止する |
| `requestPermission` | `level`: `whenInUse` / `always` | 結果 | 4.4 の2段階昇格に対応 |
| `getStatus` | — | status | 権限状態・監視状態・キュー長・最終送信成功時刻・最終エラー |
| `enqueueBoardingHint` | `answer`, `stop_id` | `event_id` | **Dart がイベントを生む唯一の経路** |
| `flushNow` | — | void | 前景復帰時およびデバッグ用 |
| `getRecentEvents` | `limit` | イベント配列 | デバッグ画面用 |

**Native → Dart**

初期段階では設けない。前景での状態表示は `getStatus` のポーリングで足りる。EventChannel の導入は必要が生じてからとする。

## 5. サーバー側 集計ロジック

### 5.1 待機セッションの構成

`region_enter` を起点に**待機セッション**を開く。

```
session {
  session_id
  anon_token          # 匿名利用者識別子
  stop_id             # のりば (第2段判別の結果)
  t_in                # 進入時刻
  t_out               # 離脱時刻 (確定は 5.2 以降)
  wait_seconds        # t_out - t_in
  status              # open / closed / discarded
  validated_by        # roundtrip / velocity / none
}
```

### 5.2 発車イベントの検出

#### 5.2.1 出発側のみを見る方式が破綻する理由

初版 (v0.1) では、同一のりばの `region_exit` 時刻を1次元クラスタリング (eps = 90秒) し、クラスタ内中央値を発車時刻としていた。**この方式は混雑時に破綻する。**

出発側の退出検知は「退出検知の遅延のばらつきが発車間隔より小さい」ことを暗黙に前提とするが、混雑時にはこれが崩れる。

```
発車1 (t=0)   の乗客 → 退出検知は t=0〜300秒に分散 (iOS ヒステリシス)
発車2 (t=300) の乗客 → 退出検知は t=300〜600秒に分散
                          ↑ 重なる
```

離脱候補時刻が eps 以内で連鎖すると、DBSCAN は複数便を1クラスタに融合する (chaining)。**増発により発車間隔が詰まる混雑時ほど発生しやすく、測定対象である混雑そのものが測れなくなる。** 閑散時には正常に動作するため小規模テストでは発覚せず、`eps` や `min_samples` の調整でも解決しない — 遅延のばらつきと発車間隔が同オーダーに達した時点で、密度ベースの分離は原理的に不可能である。

本キャンパスの利用実態は**時間帯による差が極端**であり (1・2限後は数人、大コマ終了後は300人超)、閑散レジームと混雑レジームの双方を同一アルゴリズムで扱う必要がある。

#### 5.2.2 観測点を着地点に移す

**同一の便に乗った乗客は、着地点リージョンに物理的に同時刻に進入する。** 1台の車両に同乗しているため当然である。リージョン半径は150mであり、バス停の150m手前で全員が同時に発火するため、**降車に要する時間のばらつきすら入らない**。

| 観測点 | 端末の状態 | ばらつきの要因 | 想定オーダー |
|---|---|---|---|
| 出発側 `region_exit` | 静止 → 移動への遷移 | exit のヒステリシス、静止時の測位省電力化 | 分 |
| 着地点 `region_enter` | 移動中 | enter の検知遅延のみ | 秒 |

着地点の enter クラスタは、実質的に**バス車両そのものの位置を観測している**ことに等しい。乗客の端末を通じて、車両にGPSを積んだのとほぼ同等の情報が得られる。発車間隔が5分に詰まる混雑時において、ばらつきが分オーダーか秒オーダーかが分離可能性を決定する。

> **この優位性は物理的な根拠に基づく仮定であり、iOS / Android の enter 判定の実挙動は未検証である。** 11章の実測プロトタイプで検証する。検証結果によらず壊れないよう、5.2.3 では**両側のクラスタを算出し、分離度の高い方を採用する**。

#### 5.2.3 二層構造

5.4 が「往復照合が主経路、速度判定は暫定シグナル」という構造を採っているのと同じ形を、発車イベント検出にも適用する。

| | **層1: 確定推定** | **層2: 速報推定** |
|---|---|---|
| 観測点 | 着地点の `region_enter` | 出発側の `region_exit` |
| 確定タイミング | 15〜35分後 (バッチ) | 即時 |
| 用途 | `missed_buses`、履歴、ベースライン | リアルタイム表示のみ |
| `confidence` | high | low |
| 事前情報 | — | 時刻表 (5.2.5) |

**層1の手順**

1. 着地点リージョンの `region_enter` 時刻を `region_id` ごとに1次元クラスタリングする (eps は出発側より小さく取る。初期値45秒、要較正)
2. 形成されたクラスタを **1便の到着**とみなす
3. `trip_matches` (5.4) 経由で、各メンバーを出発側セッションに逆写像する
4. 逆写像されたセッション群の出発側 `region_exit` 検知時刻の集合から `t_departure` を推定する
5. 所属セッションの `t_out` を `t_departure` にスナップして再計算する

**手順4で中央値を用いない。** 便が識別済みである以上、退出検知の遅延 ε は真の発車時刻に対して**片側 (ε ≥ 0)** にしか分布しない。この状況で中央値を採ると系統的に遅れる。真値に最も近いのは下側の統計量である。

ただし最小値は誤検知 (乗車前にリージョンを出た者) に脆いため、**下位10〜20パーセンタイルを用いる** (較正対象)。

> v0.1 が中央値を指定していたのは「便が識別できていない状態でクラスタ内のばらつきを吸収する」文脈においてであり、便が確定した後の推定量としては誤りである。**層2では依然として中央値を用いる** — 層2は便が識別できていない状態だからである。

**層1が扱えないもの**

- 往復照合が成立しないセッション (途中下車、駅で解散等) は層1に寄与しない。母数が減る
- 層1は最短でも15分遅れる。5.6 の直近ウィンドウには間に合わない

#### 5.2.4 自己較正

層1で便が確定すると、そのメンバーの出発側 `region_exit` 検知時刻の分布が、**そのまま退出検知の遅延分布 ε の実測値になる**。

システムは稼働するにつれて自身の較正データを生成する。初期は層1に依存し、ε の分布が蓄積するにつれて層2の推定精度が向上する。10章の未決事項#2 (照合ウィンドウの較正) も同じデータから解ける。

#### 5.2.5 時刻表の利用

スクールバスには大学が公表する運行ダイヤ (PDF) が存在する。これを事前情報として層2に与える。

発車時刻を完全にデータから発見するのではなく、**既知の候補時刻への割り当て問題**として扱うことで、以下が改善する。

- 観測数が少ない閑散時 (クラスタが形成されない時間帯) でも発車時刻を推定できる
- 8章のコールドスタート期間において、履歴が皆無でも動作する
- ダイヤに存在しない密集を検出することで、**増発便を「ダイヤからの逸脱」として同定できる**

ダイヤは `timetables` テーブル (6.1) に取り込む。PDF からの取り込みは手動でよい (改訂頻度が低いため)。

> **未確定 (未決事項#9)**: 増発が「ダイヤに記載された増発便」なのか「現場判断による随時増発」なのかが未確認。後者の場合、混雑時ほどダイヤからの逸脱が大きくなるため、時刻表の事前情報としての価値が下がる。実運用の観察により確認すること。

#### 5.2.6 出力

```
departure {
  departure_id
  stop_id
  t_departure
  member_count
  confidence          # high / low
  layer               # confirmed (層1) / provisional (層2)
  source              # arrival_cluster / departure_cluster / timetable
  arrival_cluster_id  # 層1のみ
}
```

層2で生成した `provisional` な発車イベントは、後に層1が同一の便を確定した時点で**置換する**。層2の推定値を履歴・ベースラインに混入させないこと。

利用者が1人しかいない時間帯ではクラスタが形成されない。この場合は時刻表上の最も近い発車時刻を用い、`confidence` を下げて記録する — エラーにはしない。

### 5.3 見送り本数の算出

あるセッションの滞在区間 `[t_in, t_out]` に含まれる発車イベントの数を数える。

```
missed_buses = |{ d ∈ departures : stop_id 一致 ∧ t_in < d.t_departure < t_out }|
```

`missed_buses >= 1` は「1本目に乗れなかった」ことを意味する。**体感の混雑度は列の長さではなく「1本目に乗れるかどうか」で決まる**ため、待ち時間と並ぶ主要指標として扱う。

**算出には層1 (`layer = confirmed`) の発車イベントのみを用いる。** 層2の速報値は便の取りこぼしと過剰検出の双方を含むため、本数を数える用途には使えない。結果として `missed_buses` は15〜35分遅れて確定する。リアルタイム表示における扱いは7章で定める。

### 5.4 乗車の確定 (往復照合)

バス停エリアに入っただけの通過者を排除するため、**着地点への到着をもって乗車を確定する**。

| 出発 | 到着 | 判定 |
|---|---|---|
| `st_hachioji` 退出 | `campus_area` 進入 | 乗車確定 |
| `st_minamino` 退出 | `campus_area` 進入 | 乗車確定 |
| `campus_area` 退出 (八王子駅行き判別済) | `st_hachioji` 進入 | 乗車確定 |
| `campus_area` 退出 (みなみの駅行き判別済) | `st_minamino` 進入 | 乗車確定 |

**照合ウィンドウ**: 退出から 15〜35分 (設定値。実測による較正が必要 — 10章参照)

この照合は**両方向で対称に成立する**。当初キャンパス側の乗車判定として検討していた「道路方向に20km/h以上で離脱」という速度ベースの推定は、着地点ジオフェンスによる確証で置き換えられる。速度判定は**照合成立前の暫定シグナル (早期の混雑度更新用) およびフォールバック**として残す。

### 5.5 セッションの除外条件

以下は統計から除外する (生データは保持)。

| 条件 | 想定される実態 |
|---|---|
| `wait_seconds < 60秒` | 通過者 |
| `wait_seconds > 60分` | 駐車・滞留・イベント欠落 |
| `validated_by = none` | 乗車が確認できない (買い物客・在室者等) |
| `stop_id = pending` | のりば判別に失敗 |

### 5.6 混雑度の導出

待ち時間の絶対値ではなく、**同一条件下の履歴に対する相対値**として算出する。指標は2系統あり、更新頻度と精度が異なる。

#### 5.6.1 確定指標 (層1由来)

```
baseline = 同一のりば × 同一曜日 × 同一時限帯 の過去の待ち時間分布
level    = 直近ウィンドウ (例: 15分) の待ち時間中央値が baseline の何パーセンタイルか
```

「今4人待っている」には意味がないが、「同じ曜日・同じ時限の履歴で上位10%」には意味がある。`missed_buses` の直近平均も併せて提示指標とする。

精度は高いが、5.2 の層1に依存するため**15〜35分遅れて確定する**。履歴とベースラインの構築はこの指標のみを用いる。

#### 5.6.2 即時指標 (層0)

`region_enter` は退出と異なりヒステリシスの影響を受けず、**ほぼ遅延なく到達する**。したがって「現在バス停エリアに滞在しているアプリ利用者のセッション数」は即時に得られる。

```
入力     = 同一のりばの未クローズセッション数 (status = open)
baseline = 同一のりば × 同一曜日 × 同一時限帯 の過去のセッション数分布
level    = 現在のセッション数が baseline の何パーセンタイルか
```

**これは 1.3 の「人数を数えない」に違反しない。** 1.3 が禁じているのは観測人数から**実人数を推定する**経路であり、アプリ普及率が不明である以上その推定は原理的に成立しない。5.6.2 が行うのは相対比較であり、普及率は baseline 側にも同じように作用して相殺される。5.6.1 が待ち時間に対して行っていることを、セッション数に対して適用したにすぎない。

ただし成立には以下の条件が伴う。

- **セッション数を表示してはならない。** 出力は段階値のみとする (7.6)
- **baseline を長期固定にしない。** 普及率は学期をまたいで変動するため、履歴と現在で普及率が異なると相殺が壊れる。**直近数週間に限定する** (期間は較正対象)
- 通過者が混入する。5.4 の往復照合を経ていないため、駅前の通行人やコンビニ客を含む。相対比較により部分的に相殺されるが、**層1の精度には及ばない**
- 普及率が低い初期は常時0〜1人となり分解能を持たない (8章)

#### 5.6.3 両者の役割分担

| | 5.6.1 確定指標 | 5.6.2 即時指標 |
|---|---|---|
| 由来 | 層1 (着地点クラスタ) | 層0 (`region_enter`) |
| 遅延 | 15〜35分 | ほぼゼロ |
| 精度 | 高 | 粗 |
| 用途 | **履歴・baseline の構築**、`missed_buses` | **現在値の表示** |

**baseline の構築に 5.6.2 を用いてはならない。** 通過者を含むため、履歴が汚染される。

サンプル数が閾値を下回る場合はいずれの指標も算出せず、その旨を明示する (表示方法は7章)。閾値は統計的要求と 9.5 の k-匿名性要求の**大きい方**を採る。

**相対値であることが 5.2 の要求を軽くしている。** 本節が履歴分布に対するパーセンタイルを採るため、`t_out` に**一定のバイアス**が乗っていても、比較対象である履歴側にも同じバイアスが乗り**相殺される**。

したがって 5.2 が解くべき課題は「バイアスの除去」ではなく、**「分散の低減」と「`missed_buses` の算出」の2点のみ**である。特に層2 (速報推定) は、バイアスを問わず分散だけ抑えれば実用に足る。

ただしこの相殺が成立するのは**バイアスが履歴と現在で等しい場合に限る**。OSのバージョン更新やライブラリ差し替えによって検知遅延の特性が変わった場合、履歴との連続性が断たれる。そのような変更を行った際はベースラインを再構築すること。

### 6.2 API

**POST /v1/devices**

デバイス登録。`anon_token` と `device_token` を払い出す。

**認証は大学の Google Workspace アカウント (`edu.teu.ac.jp`) に限定する** — ID トークンの `hd` クレームを検証し、他ドメインを拒否する。

**本エンドポイントは認証サーバー側に属し、収集サーバーとは分離する** (9.2)。`anon_token` はランダムに生成して端末へ返し、**認証サーバー側には保存しない**。認証サーバーが保持するのは `auth_registrations` (6.1) のみである。

`issue_count` が上限 (年3回) に達している場合は拒否する。

**POST /v1/events**

イベントのバッチ送信。`event_id` により冪等。`Content-Encoding: gzip`。

```json
{
  "schema_version": 1,
  "device_sent_at": "2026-08-10T09:20:15.123+09:00",
  "events": [
    {
      "event_id": "9f8e7d6c-…",
      "type": "region_enter",
      "occurred_at": "2026-08-10T09:12:03.480+09:00",
      "region_id": "campus_area",
      "stop_id": null,
      "payload": { "accuracy": 12.4 }
    }
  ]
}
```

`occurred_at` はミリ秒精度・オフセット付き ISO 8601。ミリ秒は 5.2 のクラスタリング (eps = 90秒) に対しては過剰だが、`stop_resolved` の再測位間隔の較正に用いる。

**種別ごとの `payload`**

| type | payload |
|---|---|
| `region_enter` / `region_exit` | `accuracy` |
| `stop_resolved` | `resolved` (`hachioji_bound` / `minamino_bound` / `pending`), `d_a`, `d_b`, `accuracy`, `attempts`, `elapsed_ms` |
| `motion_sample` | `lat`, `lon`, `speed`, `heading`, `accuracy`, `context` (`stop_resolution` / `exit_window`) |
| `boarding_hint` | `answer` (`boarded` / `missed`), `stop_id` |

`stop_resolved` が `attempts` と `elapsed_ms` を持つのは、未決事項#3 (35m しきい値の較正) が `pending` 率の実測を前提としているため。何回目の再測位で確定したかが残らなければ、60秒という打ち切り時間そのものを較正できない。

レスポンスは受理した `event_id` の一覧のみを返す。判定結果は返さない (端末は判定に関与しないため)。

**GET /v1/config**

リージョン定義と較正値を配信する。端末はこれをネイティブ側に永続化し (4.5)、以降はキャッシュで動作する。

```json
{
  "config_version": 3,
  "regions": [
    { "id": "campus_area",  "lat": 35.625514, "lon": 139.341597, "radius_m": 150 },
    { "id": "st_hachioji",  "lat": 35.654167, "lon": 139.339194, "radius_m": 150 },
    { "id": "st_minamino",  "lat": 35.631472, "lon": 139.329278, "radius_m": 150 }
  ],
  "stop_points": [
    { "id": "campus_hachioji_bound", "lat": 35.625806, "lon": 139.342111 },
    { "id": "campus_minamino_bound", "lat": 35.625222, "lon": 139.341083 }
  ],
  "resolution": {
    "distance_threshold_m": 35,
    "max_duration_s": 60,
    "retry_interval_s": 10
  },
  "motion_sample": {
    "rate": 0.1,
    "interval_s": 1,
    "exit_window_s": 120
  },
  "upload": {
    "jitter_max_s": 120,
    "batch_size": 200
  }
}
```

**`motion_sample.rate` によるサンプリング。** `motion_sample` の用途は 5.4 の速度フォールバックと 10章の較正に限られ、いずれも統計的に十分な標本があれば足りる。全端末から全数を集める必要はない。端末は自身の `anon_token` のハッシュ値により対象か否かを判定する。較正が完了した後は `rate` を `0` にして停止できる。

これは端末による判定ではない — 送信するか否かを決めているのはサーバーであり、端末は配信された設定に従うだけである。

**しきい値をアプリに埋め込まないこと。** 10章の未決事項#2・#3 はいずれも実測による較正を前提としており、埋め込むと較正のたびに再ビルドと再配布 (TestFlight の審査待ちを含む) が必要になる。

**セッション数・待機人数をレスポンスに含めない** (7.6)。層0が内部でセッション数を用いることは、それを外部に出す許可を意味しない。

**GET /v1/congestion/history**

時限帯別・曜日別の履歴。ベースライン提示および画面表示用 (7章)。

## 7. 混雑度の提示方法

本章は表示の意匠ではなく、**何を表示できるか / してはならないか**を定める。意匠は本章の制約の下で別途設計する。

### 7.1 主表示の構成

利用者の判断に必要な情報は3つであり、いずれも既存の仕組みから得られる。

| 要素 | 由来 | 遅延 |
|---|---|---|
| **現在の混雑度** | 5.6.2 即時指標 (層0) | ほぼゼロ |
| **この時間帯の通常値** | 5.6.1 の baseline | — (履歴) |
| **次の発車まで** | 時刻表 (5.2.5) | — |

**現在値と通常値を併記することが本章の中核である。**

設計書 1.1 は「今バス停に向かうと、どのくらい待つか」を目的とするが、これは**予測**の要求である。一方 5.6 が算出するのは**現況**であり、両者にはずれがある。利用者がバス停に到達するのは10〜20分後だからである。

このずれは**大コマ終了直前に最大となる**。

```
14:35  アプリを見る → 現況は空いている  ← 授業がまだ終わっていないため
14:40  大コマ終了
14:50  バス停に到着     → 実際には混雑
```

現況のみを表示すると、**最も情報を必要とする局面で最も誤った情報を与える**。

これを解くために予測を行う必要はない。**「現在 Lv.1 / この時間帯は通常 Lv.3」と併記すれば、利用者自身が判断できる。** システムが予測を断言するより、判断材料を示す方が 7.5 のフィードバックにも配慮できる。

### 7.2 段階の定義

混雑度は4段階とする。段階値の意味は 5.6 のパーセンタイルに直結させる。

| 段階 | パーセンタイル | 意味 |
|---|---|---|
| Lv.0 | 〜50 | 待たずに乗れる見込み |
| Lv.1 | 50〜75 | 通常 |
| Lv.2 | 75〜90 | やや待つ |
| Lv.3 | 90〜 | **1本見送る可能性がある** |

**境界を等間隔にしない。** 上位を細かく取るのは、混雑側ほど識別の価値が高いためである。Lv.0 と Lv.1 の区別は利用者の行動を変えないが、Lv.2 と Lv.3 の区別は「今出るか、10分後に出るか」を変える。

**Lv.3 を `missed_buses` の言語化とする。** 5.3 が「体感の混雑度は列の長さではなく1本目に乗れるかどうかで決まる」としているため、最上位の段階がそれを直接表すことで、集計上の主要指標と表示が一致する。

表現形式は人型アイコン等の強度表示を想定する (鉄道の混雑度表示に準じ、学習コストが低い)。ただし後述 7.6 の制約を満たすこと。

### 7.3 データが不足する場合

サンプル数が閾値を下回る場合 (5.6.3)、**Lv.0 を表示してはならない。** 「空いている」のではなく「分からない」のであり、同一のスケール上に置くと「Lv.0 より空いている」と誤読される。

- 混雑度の表示領域は無効状態とし、データが不足している旨を明示する
- 代わりに**時刻表から「次の発車まで○分」を表示する**

時刻表は履歴を必要としないため、**閑散時にも 8章のコールドスタート期間にも常に表示できる**。混雑度をアプリの唯一の機能とせず、時刻表を土台に据えることで、データが揃わない状況でも画面が成立する。

### 7.4 確定指標の遅延の扱い

`missed_buses` および実測待ち時間は 5.6.1 に依存するため15〜35分遅れる (未決事項#11)。

- これらを**現在値として表示しない**
- 補助情報として表示する場合は、**必ず時点を明示する** (例:「25分前時点の実績」)
- 主表示は 7.1 の3要素とし、確定指標は副次的な位置に置く

### 7.5 フィードバックループへの配慮

千人規模の利用者が同一の表示を見る場合、**「空いている」という表示自体が人を動かし、混雑を作る**。逆も生じる。観測結果の提示が観測対象を変える構造である。

本設計は以下によりこれを緩和する。

- **段階を4つに留める。** 分解能が高いほど誘導が強くなる
- **人数を表示しない** (7.6)。絶対数は最も強い誘導力を持つ
- **予測を断言しない。** 7.1 の通り現在値と通常値の併記に留め、判断を利用者に委ねる
- 5.6.1 の遅延は、皮肉にもループを弱める方向に作用する。未決事項#11 で問題視した遅延が、ここでは緩和要因となる

完全な解消は原理的に不可能である。**運用開始後、特定ののりばの混雑度が短周期で振動していないかを観察すること。**

### 7.6 表示してはならないもの

| 禁止 | 根拠 |
|---|---|
| 待機人数・セッション数・観測人数 | 1.3。層0が内部でセッション数を用いることは表示の許可を意味しない |
| 待ち時間の絶対値を主表示にすること | 5.6。「待ち10分」ではなく相対値に意味がある。補助表示は可だが 7.4 の時点明示を伴う |
| 個人の待ち時間・滞在時間 | 9章 |
| 4段階を超える細分化 | 7.5。統計的精度も伴わない |
| データ不足を Lv.0 として表示すること | 7.3 |

### 7.7 `boarding_hint` の取得

4.1 の `boarding_hint` (乗れた / 見送った) は任意回答であり、回答率が低ければデータにならず、頻繁に求めれば利用体験を損なう。

- **プッシュ通知では求めない** (7.5 のループおよび 9章の観点)。利用者がアプリを開いた際にのみ表示する
- 5.4 の往復照合が成立したセッションは層1で足りるため、**照合が成立しなかったセッションを優先して尋ねる**
- 頻度に上限を設ける (例: 1日1回)

### 7.8 プッシュ通知

**初期段階では実装しない。** 7.5 のフィードバックを増幅し、9章のプライバシー方針とも緊張する。必要性が実証された段階で改めて検討する。

## 9. プライバシーとデータ保持方針

**本システムの位置づけ**: 個人開発・有志プロジェクト。大学の公式サービスではない。ただし後述 9.7 の通り、学内サーバーと大学アカウント認証を用いるため、**学内規程の適用外ではない**。

### 9.1 前提: 収集するもの・しないもの

4.2 の設計により、プライバシー上の最悪ケースは既に構造的に排除されている。**9章はこの資産の明文化から始まる。**

| | |
|---|---|
| 位置を記録する場面 | のりば判別中 (最大60秒)、`region_exit` 前後 (最大120秒) のみ |
| 常時測位 | **行わない** |
| 3リージョン外での動作 | **何も記録しない** |

すなわち利用者に対して以下を保証できる。

> **このアプリは、大学と最寄り2駅の周辺以外では、位置を一切記録しません。**

自宅、アルバイト先、通学経路の途中はいずれも記録対象外である。この保証は 4.2 に依存しているため、**測位ウィンドウを拡大する変更はプライバシー方針の変更を伴う**。安易に広げないこと。

### 9.2 匿名IDの設計: 認証と収集の分離

Google アカウント認証を導入する以上、素直に実装すると `users` に `sub` と `anon_token` が並ぶ。この瞬間、**「誰が、何限に大学へ来て、何時に帰ったか」の数ヶ月分の記録が個人に紐付く**。バス停の記録のみであっても生活パターンはほぼ完全に復元できる。

これを避けるため、認証と収集を分離する。

```
[認証サーバー]                            [収集サーバー]

 Google OIDC で sub を検証
 hd == edu.teu.ac.jp を確認
        ↓
 hash(sub) → { issued_at, issue_count }     anon_token → イベント
   ※ anon_token は保存しない                  ※ 誰であるかを知らない
        ↓
 ランダムな anon_token を生成し端末へ ────→  以降、端末はこれのみを送る
```

- 認証サーバーは「この人物が登録済みか」のみを知る。どの `anon_token` を発行したかは**保存しない**
- 収集サーバーは `anon_token` のみを知る。それが誰かを知らない
- `issue_count` に上限 (年3回) を設け、機種変更・再インストールに対応しつつ大量発行を防ぐ

**決定的ハッシュ (`anon_token = HMAC(secret, sub)`) は採用しない。** 再インストール時に同一IDを復元できる利点はあるが、学籍番号ベースのメールアドレスは候補が有限であり、`secret` が漏洩すれば**総当たりで全利用者を逆引きできる**。匿名性が見かけ倒しになる。

### 9.3 技術で保証できない部分

**上記の分離は完全な匿名化ではない。** 両サーバーを同一の管理者が運用する以上、認証ログの発行時刻と収集側の初回イベント時刻を突合すれば、紐付けは技術的に可能である。

したがって以下を**運用上の約束**として明示する。技術的保証と運用上の約束を混同して記述しないこと。

- 認証サーバーと収集サーバーのログを突合しない
- 認証サーバーのアクセスログの保持期間を7日とする
- 管理者権限を持つ者を限定し、記録する

利用者への説明においても、「技術的に不可能」ではなく「そうしないと約束している」と正確に述べる。

### 9.4 データ保持と段階的匿名化

削除ではなく**段階的匿名化**を軸とする。`anon_token` を除去すれば較正データとしての価値は保たれ、個人の行動履歴ではなくなる。これは 5.5 の「生データは消さない」原則と両立する。

| データ | 保持 | 根拠 |
|---|---|---|
| `motion_sample` (座標そのもの) | **90日で削除** | 最もセンシティブ。較正専用であり、完了後は `motion_sample.rate: 0` で収集自体を停止できる |
| `region_enter` / `region_exit` / `stop_resolved` | 13ヶ月間は `anon_token` 付き。以後は `anon_token` を除去して保持 | 13ヶ月は前年同時期との比較に必要な最小期間 (学年暦が1年周期のため) |
| `sessions` / `boarding_hint` | 同上 | |
| 集計済みベースライン | 無期限 | 個人に紐付かない |
| 認証サーバーのアクセスログ | 7日 | 9.3 |

**削除要求**

端末から `anon_token` を提示することで、当該IDに紐づく全データを削除できる。

ただし**アンインストール後は本人であっても削除要求を出せない** — `anon_token` を保持しているのは端末のみだからである。これは 9.2 の分離設計の代償であり、9.4 の自動的な段階的匿名化が実質的な保護手段となる。**アプリ内に「削除してから削除する」導線を置き、アンインストール前に実行するよう促すこと。**

### 9.5 再識別リスクと k-匿名性

`anon_token` が匿名であっても、**行動パターンそのものが識別子として機能する**。「毎朝1限にみなみの駅から乗る人」が2人しかいなければ、実質的に特定可能である。

ここで 5.6 のサンプル数閾値が効く。これは統計的信頼性のために導入された規定だが、**同時に k-匿名性の保護としても機能している**。

**閾値は「統計的に必要な値」と「k-匿名性として必要な値」の大きい方を採る。** 早朝・夜間などの少人数時間帯では、統計的には算出可能であってもプライバシー上は表示すべきでない場合がある。

### 9.6 利用者への説明と同意

4.4 の権限取得フローと統合する。**「使用中のみ許可」を要求する前に**、以下を説明する。

1. **本システムが大学の公式サービスではなく、有志による個人プロジェクトであること** — 誤認させてはならない
2. 記録するのは大学と最寄り2駅の周辺のみであること (9.1)
3. Google アカウントは「大学関係者であること」の確認にのみ使い、収集データとは分離すること (9.2)、およびその限界 (9.3)
4. 保持期間 (9.4)
5. いつでも停止・削除できること、およびアンインストール前に削除する必要があること

### 9.7 実務上の前提条件

**「個人開発だから学内規程の適用外」は成立しない。** 学内サーバーと大学アカウントを用いる以上、以下の手続きが実装の前提となる。

| 前提 | 内容 |
|---|---|
| **学内サーバーの利用申請** | 情報システム部門への申請が必要。申請時点で大学は本システムを認知した状態になり、大学側にも一定の責任が生じる |
| **Google Workspace の OAuth クライアント登録** | `edu.teu.ac.jp` の Workspace 管理者が外部アプリのアクセスを制限している場合、**承認なしには認証自体が成立しない**。実装上のブロッカーとなりうるため最優先で確認すること |
| **説明資料の作成** | 上記2つの申請過程で、収集内容・保持期間・匿名化方式の説明を求められる。**その資料が実質的に本章の外部向け版となる** |

大学の後ろ盾がない有志プロジェクトが学生の位置情報を預かる以上、**規程が要求する水準ではなく、それより厳しい水準を自主的に設定する**方針を採る。本章の保持期間・分離設計はその考えに基づく。

指導教員または情報システム部門への事前相談を推奨する (10章 未決事項#6 の伏見先生が窓口として自然)。

## 11. 初期実測プロトタイプ

本格実装に先立ち、実機による測定を行う。**目的は 5.2.2 の仮定の検証**であり、副次的に較正値の初期値を得る。

このプロトタイプは 4.5 のネイティブ層の最小実装そのものであり、**本実装にそのまま引き継ぐ**。捨て実装ではない。

### 11.1 測定項目

| 項目 | 方法 | 効く先 |
|---|---|---|
| **着地点 `region_enter` の検知遅延** | 前景の高精度測位で真の境界通過時刻を記録し、`didEnterRegion` 発火時刻との差を取る | **5.2.2 の仮定 — 最重要** |
| 出発側 `region_exit` の検知遅延 | 同上 (`didExitRegion`) | 層2の設計、ε の分布 |
| **同一便に乗った2端末の検知時刻差** | iPhone 2台を同じバスに乗せ、双方の enter / exit 発火時刻を比較 | **層1の成否を直接決める数値** |
| 半径150mでの取りこぼし率 | 通過回数に対する発火回数の比 | 3.1 の半径の妥当性 |
| 2段判別の `pending` 率と確定所要秒数 | `stop_resolved` の `attempts` / `elapsed_ms` | 未決事項#3 (35m しきい値) |
| 走行所要時間の分布 | 出発側 exit から着地点 enter までの実測 | 未決事項#2 (照合ウィンドウ 15〜35分) |
| OS 差 | Android 実機で同一項目を測定 | 4.3 の OS 別対策 |

### 11.2 「同一便2端末」の測定が決定的である理由

11.1 の3項目目が、層1が成立するか否かを単独で決める。

同じバスに乗った2台の端末の `region_enter` 発火時刻の差が**数十秒に収まるなら**、発車間隔5分の混雑時でも便を分離できる — 層1は成立する。**数分に及ぶなら**、着地点も出発側と同様に chaining し、5.2 の再設計そのものをやり直す必要がある。

iPhone 2台が既にあるため、この測定は最小の労力で実行できる。**他のどの測定よりも先に行うこと。**

### 11.3 測定時の注意

- **前景での高精度測位とリージョン監視を同時に走らせる。** 前者が「真の時刻」の基準、後者が「検知時刻」となる。両者の差が求める遅延である
- 測定は**バス乗車中に実際に行う**。徒歩や自動車での代用は、速度と経路が異なるため成立しない
- 時間帯を分けて複数回測る。混雑時と閑散時では乗車に要する時間が異なり、`region_exit` の遅延に影響しうる
- 測定結果は `raw_events` と同一のスキーマ (6.2) で記録する。本実装のサーバーでそのまま解析できる
