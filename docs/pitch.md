# 発表・審査向け 説明骨子

**目的**: `docs/design.md` (v0.2) の内容を、コンテスト・発表・審査の文脈で説明するための構成案。
設計そのものは変更しない。**説明の順序と語彙のみを組み替えたもの。**

**扱う課題**: 「AI の要素がどこにもない」という指摘への回答。
結論から言うと、この設計には既に教師なし学習と自己教師あり較正ループが入っており、
設計書がそれを実装用語 (「1次元クラスタリング」) でしか書いていないことが原因。

---

## 0. 全体の方針

**後付けで AI を飾らない。** 既に入っているものを正しい名前で呼び、
使っていない箇所については「使わない判断をした理由」を語る。

審査で強いのは「LLM を呼びました」ではなく、
**アルゴリズムの failure mode を理解した上でデータの取り方を設計し直した**という筋書き。
この設計にはそれが実在する (5.2.1 → 5.2.2)。

---

## 1. 何を作るか (30秒)

東京工科大学 八王子キャンパスのスクールバス待ち行列を、
**追加の固定設備なしに**可視化する。利用者は「今バス停に向かうとどのくらい待つか」を事前に知る。

- 対象: キャンパス + 八王子駅 + 八王子みなみ野駅 の3箇所
- 手段: 利用者のスマートフォンのジオフェンス (位置監視) のみ
- 規模想定: 利用者千人超。ピーク時の同一のりば待機は300人超

> **掴み**: 大コマ終了後のバス停には300人が並ぶ。今そこに行くべきか、
> 15分待ってから行くべきかを判断する材料が、現状は何もない。

---

## 2. なぜ難しいか — 素朴な解法は全部壊れる (2分)

ここが発表の主戦場。**「思いつく解法を順に潰していく」構成にすると、
最終的な設計の必然性が伝わる。**

### 素朴案1: 人数を数える

→ **原理的に破綻する。** アプリの普及率が不明なため、
観測できた人数から実人数を推定する経路が存在しない。
「10人観測 = 普及率10%なら100人、20%なら50人」を区別する手段がない。

**→ 判断: 人数ではなく、一人あたりの「バス停到着 → 乗車」所要時間を測る (設計書 1.3)**
この方式は観測者が1人でも成立し、普及率に依存しない。

### 素朴案2: バス停を出た時刻を見れば発車が分かる

→ **混雑時にだけ壊れる。** iOS のリージョン退出判定には独自のヒステリシスがあり、
実際の退出から**数分遅れて**発火する。

```
発車1 (t=0)   の乗客 → 退出検知は t=0〜300秒に分散
発車2 (t=300) の乗客 → 退出検知は t=300〜600秒に分散
                          ↑ 重なる
```

遅延のばらつきが発車間隔と同オーダーに達すると、
クラスタリングは複数便を1つに融合する (chaining)。

**そして増発により発車間隔が詰まる混雑時ほど、これが起きやすい。**
つまり**測りたい混雑時に限って測れなくなる**。閑散時は正常に動くため、小規模テストでは発覚しない。

> **ここが発表の山場。** 「パラメータ調整で直りませんか」への答えを用意しておく:
> 直らない。遅延のばらつきと発車間隔が同オーダーになった時点で、
> 密度ベースの分離は原理的に不可能。

## 3. 中核アイデア: 観測点を移す (2分)

**同じバスに乗った乗客は、目的地側のバス停に物理的に同時刻に到着する。**
1台の車両に同乗しているのだから当然である。

| 観測点 | 端末の状態 | ばらつきの要因 | 想定オーダー |
|---|---|---|---|
| 出発側 (退出) | 静止 → 移動 | 退出ヒステリシス、静止時の省電力化 | **分** |
| 着地点 (進入) | 移動中 | 進入の検知遅延のみ | **秒** |

さらに、リージョン半径は150m。**バス停の150m手前で全員が同時に発火するため、
降車に要する時間のばらつきすら入らない。**

> **一番伝わる言い方**:
> 着地点の進入クラスタは、実質的に**バス車両そのものの位置を観測している**ことに等しい。
> 乗客の端末を通じて、**車両に GPS を積んだのとほぼ同等の情報**が得られる。

これが同じ DBSCAN を「壊れる場所」から「働く場所」へ移した、という話。
**アルゴリズムを変えたのではなく、アルゴリズムが機能する条件を満たすようにデータの取り方を変えた。**

## 4. ここに機械学習がどう入るか (2分)

**「AI の要素は？」への直接の回答。**

### 4.1 教師なし学習 — DBSCAN の適用設計

発車イベントの検出には **DBSCAN (密度ベースクラスタリング)** を用いる。
これは教師なし学習アルゴリズムそのものである。

ただし本設計の主張は「DBSCAN を使いました」ではなく:

- **どこに適用すると壊れるかを特定した** (出発側: 混雑時に chaining)
- **壊れない観測点を設計で作り出した** (着地点: ばらつきが桁で小さい)
- **どちらが優れているかをデータで決める構造にした** (両側のクラスタを算出し、分離度の高い方を採用)

### 4.2 自己教師あり学習 — システムが自分の教師データを生成する

**この設計の最も特徴的な部分。**

```
層1 (着地点クラスタ) が便を確定
        ↓
そのメンバーの「出発側の退出検知時刻」の分布が
そのまま退出検知の遅延分布 ε の実測値になる
        ↓
層2 (出発側 = 即時に得られるが粗い推定) の精度が上がる
        ↓
リアルタイム表示の質が向上する
```

- 層1は精度が高いが **15〜35分遅れる** (バスが目的地に着くまで分からないため)
- 層2は **即時**だが粗い
- **層1が層2の教師ラベルを生成し続ける**

> **言い方**: 人手のラベル付けは一切ない。
> **システムは稼働するほど自分の学習データを蓄積し、リアルタイム推定の精度が上がっていく。**

現状は「下位10〜20パーセンタイル」という固定統計量で写像しているが、
ここは曜日・時間帯・人数・OS 種別を特徴量とする回帰に置き換えられる (拡張余地として提示可)。

### 4.3 行動認識 (実装予定) — `motion_sample` の分類

乗車の確定は「目的地に着いたか」の往復照合が主経路だが、
途中下車・駅で解散といったケースは照合が成立せず、統計の母数から落ちる。

現状はこれを「道路方向に20km/h以上で離脱」という手書きルールで補っている。
**加速度・速度系列から「バス乗車 / 徒歩 / 自転車 / 静止」を分類する行動認識 (HAR) に置き換える。**

- データ収集の仕組みは設計済み (`motion_sample`、サンプリング率はサーバー配信)
- 効果が定量的に示せる: 現行ルールで救えないセッションの割合 → 分類器で救えた割合
- 端末では判定せず**サーバー側で分類する** (後述の設計原則を守るため)

### 4.4 拡張余地 (聞かれたら)

| 適用先 | 内容 |
|---|---|
| のりば判別 | 現状は距離差35mの単一しきい値。測位ノイズの場所ごとの癖を学習すれば判別失敗を減らせる |
| 増発便の同定 | 公表ダイヤからの逸脱を異常検知として扱う |
| 短期予測 | 「10分後の見込み」。**ただし後述のフィードバックループ問題があるため慎重に扱う** |

## 5. AI を使わない判断も設計である (1分)

**攻めの守り。** 「なぜ全部を機械学習にしないのか」に先回りして答える。

### 教師信号が存在しない

「真の待ち時間」「真の発車時刻」のラベルがどこにもない。
**4.2 の着地点クラスタは、まさにその正解を物理的に作り出すための仕掛けである。**
ここを学習で置き換えようとすると、学習させる対象そのものが消える。

### コールドスタート

運用初日は学習データがゼロ。
本設計は大学公表のダイヤを事前情報として使うため、履歴が皆無でも画面が成立する。

### 分からないときは「分からない」と言う

サンプル数が閾値を下回る場合、**混雑度を算出しない。**

- 欠測を平均値等で埋めない
- **データ不足を「空いている」として表示しない** — 「分からない」と表示し、
  代わりにダイヤから「次の発車まで○分」を出す

> モデルが自信満々に外す問題への、設計上の回答。

### 説明可能性が要件

後述のプライバシー説明と、混雑度がユーザーの行動を変える問題 (フィードバックループ) の双方において、
**「なぜこの表示なのか」を答えられることが前提**になっている。

## 6. 提示方法 — 4段階のみ (1分)

| 段階 | 意味 |
|---|---|
| Lv.0 | 待たずに乗れる見込み |
| Lv.1 | 通常 |
| Lv.2 | やや待つ |
| Lv.3 | **1本見送る可能性がある** |

**設計上の主張が2つある。**

1. **絶対値ではなく相対パーセンタイル。**
   「待ち10分」ではなく「同じ曜日・同じ時限の履歴で上位10%」に意味がある。
2. **境界を等間隔にしない。** 混雑側ほど識別の価値が高いため上位を細かく取る。
   Lv.3 は「1本目に乗れるか」の言語化 — **体感の混雑は列の長さではなく、これで決まる。**

**主表示は「現在値」「この時間帯の通常値」「次の発車まで」の3要素。**
現在値だけを出すと、大コマ終了直前 (これから混む瞬間) に最も誤った情報を出すことになる。

## 7. プライバシー (1分)

**学内で運用する以上、ここは必ず聞かれる。**

- **記録するのは3箇所の周辺のみ。** 測位が動くのは「のりば判別中の最大60秒」と
  「バス停退出前後の120秒」だけ。それ以外では位置を一切記録しない
- **認証サーバーと収集サーバーを分離する。** 別データベース。認証側は誰が使ったかを、
  収集側は誰のデータかを、それぞれ単独では復元できない
- 匿名 ID はランダム生成。学籍番号やメールアドレスからの決定的な導出をしない
  (候補が有限なため、鍵が漏れると全員を逆引きできてしまう)
- 13ヶ月後に匿名 ID を除去して保持。運動データは90日で削除

> **誠実さの担保**: これらの一部は技術的保証ではなく**運用上の約束**である
> (ログを突合しない、認証ログは7日保持)。説明資料でも「技術的に不可能」とは書かない。

## 8. 現状と次のステップ (30秒)

**正直に言う。ここは隠すと後で崩れる。**

- 設計書 v0.2 完成。端末側スタック確定 (Flutter + 各 OS ネイティブの薄い層)
- **実測プロトタイプを実装中** (iOS)
- **最優先の検証項目**: 同じバスに乗せた2台の端末の、着地点での発火時刻差

この最後の1点が **3節の仮定が成立するかを単独で決める**。

- 数十秒に収まれば → 発車間隔5分の混雑時でも便を分離できる。設計は成立
- 数分に及べば → 着地点も出発側と同様に壊れる。再設計が必要

**この測定より先に集計側を作り込まない**という方針で進めている。

> **これを言うと強い**: 「未検証の仮定がどれで、それが崩れたら何が壊れるか」を
> 特定できている状態は、全部動くと主張するより信用される。

## 9. 想定質問への回答

| 質問 | 回答の骨子 |
|---|---|
| **AI の要素は？** | 4節。教師なしクラスタリングの適用設計と、層1が層2の教師ラベルを生成する自己教師あり構造。人手のラベル付けはゼロ |
| **なぜ人数を数えない？** | 普及率が不明なため観測人数→実人数の推定が原理的に成立しない。待ち時間なら観測者1人でも測れる (2節) |
| **普及率が低いうちは動かないのでは？** | 動かない期間は「分からない」と表示し、ダイヤから次の発車時刻を出す。相対パーセンタイルなので普及率は比較の両側に等しく作用し相殺される (ただし普及率が急変する時期は baseline を短期に限定する) |
| **バス停の前を通っただけの人は？** | 目的地側のバス停への到着をもって乗車を確定する。駅前の通行人・コンビニの買い物客はここで落ちる。滞在時間の下限フィルタには依存していない |
| **バッテリーは？** | 常時測位はしない。ジオフェンス発火時のみ、最大60秒の高精度測位 |
| **iOS と Android で挙動が違うのでは？** | だからこそ端末側では一切判定しない。端末は生イベントの記録・送信のみを担当し、判定はすべてサーバー側に集約する。OS 差が仕様差になることを避けている |
| **表示を見て人が動いたら予測が外れるのでは？** | 原理的に解消できない。だから4段階という粗い粒度に留め、細分化しない。運用開始後に混雑度が短周期で振動していないかを観察する |
| **既存のバスロケーションシステムとの違いは？** | あれは車両の位置を出す。本システムは**待ち行列**を出す。バスが今どこにいるかと、自分が何分待つかは別の問題 |
| **精度の検証は？** | 8節。最重要の仮定が未検証であることを明示し、検証方法と失敗時の分岐を示す |
